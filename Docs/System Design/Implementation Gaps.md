# Implementation gap register

This register compares the implemented design documents with the current code and authored content as of 2026-11-16. It deliberately verifies code rather than repeating older “current state” paragraphs that some design documents have not updated. It records missing implementation and content, not every optional polish idea.

Use [Content and balance catalog](Content%20and%20Balance%20Catalog.md) for authoring locations and [System coherence](System%20Coherence.md) for the integration plan.

**Next implementation order after commit 6:** available 640×360 manual vertical-slice acceptance is recorded. First close the integration follow-ups—quest-sourced encounter launch/completion, production return-to-menu, gamepad bindings, and Overworld/Shootout music transitions—then implement multi-target acts, effect/stat seams, and full disk save/Continue in that order. Commit scopes and exit gates are in [First steps implementation plan §11](First%20Steps%20Implementation%20Plan.md). Content expansion, secret reward claims, dynamic spawns, affix/equipment abilities, Flair and Poker integration remain later work.

## Priority meanings

- **P0 — playable-loop blocker:** a system cannot complete its intended real-game flow, or disconnected ownership can duplicate/lose progress.
- **P1 — required mechanic/coherence:** a documented first-iteration rule or shared contract is absent or contradictory.
- **P2 — content and coverage:** the machinery exists but production content, authored variety, validation, or acceptance is missing.
- **Deferred:** explicitly outside the current iteration; listed so it is not mistaken for a completed feature.

## 2. P1 missing or contradictory mechanics

### Combat and loadouts

| Gap | Current evidence and required completion |
|---|---|
| Multi-target acts resolve one actor — **next commit 1** | `positions.type: "multi"` exists and Doctor's Kit says it heals every living member, but `Shootout.selectActor()` stores one target and `resolveWithFocus()` calls the resolver once. Next implement one ordered target-set pipeline shared by player and AI: per-position taunt redirection, UI confirmation/animation/focus, death handling and once-per-act costs. Resolve the multi-target taunt stacking question in Positions and Targeting before implementation. |
| Effect-driven stat modifiers are reserved — **next commit 2** | `ShootoutEffectManager.getStatModifier()` currently returns the base value and no effect type modifies stats. Taunt redirects but does not grant its designed defensive buffs. Next define the supported-stat registry and modifier order, then route initiative, damage and UI reads through the shared `Shootout.getModifiedStat()` seam instead of direct Rodeo-only reads. |
| Jammed payload is implemented | `resolveSpecialChamber()` applies the class-authored `jammed` effects payload instead of only displaying “Jammed!”; class files own the effect data. Broader Jammed redesign remains out of scope. |
| Miss/on-hit semantics are implemented | Miss consumes the Chamber and applies no damage, no on-hit effects and no mark consumption for both weapon Moves/attacks and attack abilities; `TestActs` covers the attack-ability case. |
| Class abilities are not executable class grants | Class files contain descriptive strings such as “Attack and bleed affliction”; Party/actor `moves` contains only directly authored names. Replace descriptions with canonical Move ids or a validated grant projection, then implement out-of-combat activation within the four-move cap. |
| Equipment abilities are absent | Equipment has stats/affixes but no data contract or fight-loadout path for granted Moves. Define item-granted Move ids, activation/preview, replacement behavior, and combat validation together. |
| Unsupported affixes roll and sell without mechanics | `CharacterStatCalculator` applies only Six Shootin', High Tailin', Taffyin', Style, Sand, MxHP, the equipped weapon family's damage, and top-level belt space. Other generated stats—including explosive/lasso lines, marked/cylinder bonuses, MxEN, initiative/turn-order aliases, effect resistance/duration, piercing/reduction/taunt recovery, silence immunity, loot bonuses, and bleed/poison affliction—remain display text. Either implement each mechanic and preview or exclude it from generation/pricing until supported. |
| Zone loot is implemented | `EncounterRequest` and the Shootout carry `zoneId`, and `ItemGeneration.generateLoot()` accepts the canonical Zone, feeds it into generated equipment and fails closed to `anywhere` for unknown ids. Off-Trail fights return an empty reward payload. |
| Weapon identity has little combat differentiation | `WeaponData` bases provide id/name/sprites/value, but base damage rolls from family affix ranges; Magazines/ranges are family-wide. If individual weapons are meant to differ mechanically, author per-base combat stats rather than only economic values. |
| Dust-up/Showdown AI difficulty is undifferentiated | Both use `PICK_FROM_TOP = 2` and shared scoring. The design calls for easier/dumber Dust-ups and lower stats; implement encounter-level AI selection/weights and tune compositions. This remains after the multi-target and effect/stat seams. |
| Boss support has no boss content; per-actor thresholds are implemented | AI script loading and non-rout win conditions exist, but `Data/Shootout/AI` and unique boss actors/Rodeos/encounters/loot are absent. `hp_below` is per-actor (`actorName`, `fraction`/`amount`, optional `stat`/`winner`) with `TestEncounters` fixtures; boss-specific content remains to be authored after the foundation work. |
| Walker/story Rodeo changes are unwired | Natural Gunslinger and other Rodeo files exist, but quest completion never swaps `Party.party["Walker Langley"].rodeo` or any other story Rodeo. |
| Basic weapon attacks are removed from enemy AI | Removed from `ShootoutEnemyAI.gatherLegalActs()` and scoring; every offensive action is an authored Move. `Scratch` is authored for the Squeky rat, `TestEncounters` requires every combat actor to own an offensive Move, and Miss applies no on-hit effects for attack abilities. |

## 5. Decided rules and remaining decision

The following decisions are canonical. The implementation work is to replace legacy behavior and encode these rules in tests, not to reopen them:

1. **HP and knockouts:** ✅ implemented in commit 4 — fighters start each Shootout at effective max HP, no persistent knockout debuffs, attrition is injected and On-Trail only; Vamoose routing remains commit 5.
2. **Bleed stacking and healing:** ✅ implemented in commit 4 — combined stack counts, two stacks per damage before resistance, healing removes stacks through the cleanse path.
3. **Vamoose loss:** remove half of money and a balance-selected 10–20% of remaining carried inventory. Equipped items and Bank contents are excluded. Exact item selection/rounding inside that range is balance data and must be deterministic and atomic. (Commit 5.)
4. **Basic attacks:** ✅ implemented in commit 4 — enemy AI gathers Moves only, the rat owns `Scratch`, and content validation requires an offensive Move for every combat actor.
5. **Boss HP conditions:** ✅ implemented in commit 4 — `hp_below` targets a named base actor with `fraction`/`amount`, optional `stat`/`winner`; boss content is still missing.
6. **Zone item acquisition:** ✅ implemented in commit 4 — the encounter Zone reaches `generateLoot()` and is validated canonically; Off-Trail loot stays empty.

### Remaining decision

7. **Poker rules:** “Texas hold'em” does not by itself communicate four-card flushes or every-player blinds. Record exact house rules before economy balancing.

## 7. Explicitly deferred, not blockers

The following should not be used to inflate the required first-iteration worklist: vendor schedules/haggling/buyback/per-town Banks, general fog of war/fast travel, moving visual parties, mid-fight reinforcements, direct unequip/drag-and-drop, player-selected loot, exact level-scaled Rodeo text in Character, cross-tab shortcuts, WFC reflection/backtracking/debug visualisation, and loading-screen progress art. They require new design only after the coherent core loop works.
